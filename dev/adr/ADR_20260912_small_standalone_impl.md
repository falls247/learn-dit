# ADR: 小型独立実装と共通 Flow Matching

- 日付: 2026-09-12
- 状態: 採用

## 背景

目的は GR00T N1.7 の動作生成部分を理解することです。
既存のロボット学習フレームワーク（GR00T 本体、lerobot の学習側、diffusion policy 実装）を
そのまま使えば動くものは早く得られますが、抽象化の層が厚く、
「何が学習の本質か」が読み取れません。

## 決定

1. **小型の独立実装にする。** 学習・生成の中核は自前で書き、外部フレームワークは
   データ取得（lerobot）とシミュレータ（gym-pusht）に限定する。
2. **Flow Matching と DiT を題材間で共通化する。** MNIST と PushT で
   `flow/flow_matching.py` と `models/dit.py` を共有し、差分はトークン化と条件付けだけにする。
3. **設定は dataclass + YAML にする。** pydantic を使わず、依存を減らし
   「設定が構造体に入るだけ」であることを読み手に見せる。検証は `config.validate()` に集約する。
4. **中間値を返す損失関数にする。** `flow_matching_loss` は損失だけでなく
   `t` / `x_t` / `eps` / `v_target` / `v_pred` を返す。`inspect` がこれを使って
   教材としての説明を実数値で行う。

## 理由

- Flow Matching の中核は 60 行程度で書けます。共通化すると
  「画像生成と動作生成が同じ仕組み」という理解が一行の差分として現れます。
- トークン化を差し替えるだけで題材が変わる構造は、GR00T のような
  VLA の動作生成ヘッドを読む足場になります。
- 依存を薄くすると、バージョン不整合の調査時間が理解の時間を食いません。

## 結果

- 良い点: 読む量が少ない。テストが数学の性質を直接検証できる。題材追加が容易。
- 悪い点: フレームワークが持つ最適化（分散学習、EMA、学習率スケジュール、
  効率的なデータローダ）は入りません。性能面はフレームワークに劣ります。
- 明示的に諦めたこと: DDPM との比較、VAE 潜在空間、言語条件、実機実行。

## 代替案

- **lerobot の diffusion policy をそのまま使う**: 早いが、Flow Matching の実装を
  読む機会が失われる。
- **GR00T のコードを直接読む**: 目的には合うが、実行環境の要求が重く、
  手を動かして確認する反復が遅い。
